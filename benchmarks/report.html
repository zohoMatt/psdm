psdm vs the original EPA PSDM

Speed and agreement of the psdm package against the US EPA PSDM code it was rewritten from, on 11 cases, 7 fresh-process runs per case and implementation. Generated by scripts/benchmark.py on 2026-10-14 20:10 Eastern Daylight Time.

1.41×geometric-mean speed-up, build + run, against upstream with float64 inputs (range 1.08–2.87×)
1.04×geometric-mean speed-up inside solve_ivp (range 0.99–1.15×)
0.33 %worst max |psdm − upstream| / C0 across all cases
0.57 %worst max |psdm − AdDesignS| / C0 (single-compound cases)

The ODE algorithm is the same. Both codes integrate the same equations with scipy BDF, the same tolerances and the same Jacobian sparsity pattern. Step and RHS-evaluation counts agree within 6.5 %.

Most of the single-compound gap is an input-dtype artefact, not a psdm improvement. Upstream's single-compound inputs were built the way upstream's test_PSDM.py builds them, by transposing the data sheet of test.xlsx. That sheet mixes numbers with the string influentID, so the chemical-property and K-data frames have dtype object. The object dtype carries through to the bed coefficients, and the two np.matmul calls in upstream's right-hand side then run as Python-object loops. Built that way, upstream is 2.44–3.04× slower than psdm. Converting the same inputs to float64 (the float64 inputs column) makes upstream 2.05–2.33× faster with no change to its code, and leaves psdm only 1.08–1.42× ahead. The float64 run changes upstream's output by at most 0.29 % of C0, through a slightly different step sequence.

What psdm actually gains, against upstream with float64 inputs:

  • single compound, constant influent (7 cases): build + run 1.08–1.42×, inside solve_ivp 0.99–1.12×.
  • multi-component (2 cases): build + run 2.46–2.87×, inside solve_ivp 1.02–1.15×.
  • variable influent (2 cases): build + run 1.17–1.44×, inside solve_ivp 1.03–1.06×.

Most of that gain is outside the integrator. Upstream rebuilds per-minute tables for influent, fouling and tortuosity on every run, one point per simulated minute (about 250,000 points for 174 days and 1.44 million for the 1,000-day multi-component case), plus the Jacobian pattern; it also copies DataFrames and computes a fit residual inside run_psdm_kfit. psdm builds these on the solver's own time scale. Inside the integrator the two are close: per RHS evaluation (integrate time / RHS evaluations, which includes Jacobian and LU work) upstream takes 0.95–1.10× as long as psdm.

Solver work

All implementations call solve_ivp with BDF, default tolerances (rtol 1e-3, atol 1e-6) and the same sparse Jacobian pattern; scipy estimates the Jacobian by finite differences. Counts are from the first run and were identical in every repeat. The small differences come from floating-point round-off in different but equivalent arithmetic. Cost per RHS evaluation = warm integrate time / nfev. It includes the finite-difference Jacobian and LU work, so it is a per-step cost proxy, not a pure RHS timing.

Methods

  • Implementations. Upstream: psdm/PSDM.py from USEPA/Water_Treatment_Models at commit 3f514c2, unmodified, imported from a fresh clone. New: the psdm package from this repository. All run in the same virtual environment, so numpy, scipy and pandas builds are identical.
  • Upstream input variants. In the single-compound cases the upstream inputs are built as in upstream's test_PSDM.py and this repository's tests/data/reference/generate.py, by transposing the data sheet, which produces object-dtype frames. The float64 inputs control group applies .astype(float) to the chemical-property and K-data frames and converts the numeric entries of the column Series; nothing else changes. The multi-component and variable-influent cases read their inputs with upstream's process_input_file and process_input_data, which already return numeric dtypes, so they have no separate control group.
  • Process isolation. Each timed sample is a new python -I process that imports one implementation and runs one case twice. The order of implementations rotates per case and repeat to spread out drift from thermal or background load.
  • What is timed. build + run = upstream PSDM(...) construction plus run_psdm_kfit (single-compound and variable-influent cases, the call the upstream examples use) or run_psdm (multi-component); for psdm, building Column/Compound objects (or Dataset.compounds()) plus simulate(). Excel reading is timed separately and excluded from the headline; so are interpreter start-up and package import.
  • Cases. Single compound (TCE) from the AdDesignS verification set in tests/data/addesigns_test.xlsx (the upstream test.xlsx), constant influent for 174 d, default nr = 14, nz = 19. This adds the 25 mg/L Rhine and Organic Free cases to the five used in the test suite, because AdDesignS output exists for them. Multi-component: examples/Example_Multi.xlsx, nr = 4, nz = 8, ne = 2, as in tests/data/reference/generate.py. Variable influent: examples/Example_TCE.xlsx sheet data_variable (piecewise-linear TCE influent 3–5 mg/L), nr = 8, nz = 12, as in upstream Example_TCE.py, with and without Rhine fouling.
  • Accuracy. Effluent curves are linearly interpolated onto 349 evenly spaced times and compared; max and RMS of |psdm − upstream| / C0 are reported (for multi-component cases, the worst compound). AdDesignS comparisons use the sheets 5, 25, 50, 5no, 25no, 50no and 50K at their own output times, keeping only rows with C > 0, as in the test suite. The sheets end in negative sentinel rows, and their first rows are ±1e-3 noise. AdDesignS output stops at 105 d for the Rhine cases.

Limitations

  • One machine, one Python and library set (below). Absolute times will differ elsewhere; ratios are more portable but still depend on the BLAS and scipy version.
  • The cases are small (tens to a few hundred ODEs). Large multi-component problems were not benchmarked.
  • Upstream run_psdm_kfit also computes a sum of squares against (empty) effluent data and copies DataFrames; that overhead is part of its normal API and is counted. The solve_ivp column isolates the integrator for a like-for-like comparison.
  • Fitting routines (K/1/n search, ds fitting), capacity and uncertainty tools were not timed. Upstream's fitting loops call run_psdm many times, so the per-run setup cost above would multiply there.
  • Agreement with upstream is not agreement with reality; the only external reference here is AdDesignS.
